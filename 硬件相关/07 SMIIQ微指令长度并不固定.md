**一句话：每个模块都有自己的SMI-IQ即指令队列，FPADD有自己的SMI-IQ，UR有自己的SMI-IQ、RtoVR有自己的SMI-IQ，不是说所有指令都用一个SMI-IQ**





## 结合向量浮点加法样例的具体验证

样例中 3 类模块的微指令长度差异明显，且同一模块的指令长度一致：

|    模块     |                    微指令核心字段组合                    | 总长度（估算） |                   一致性说明                    |
| :---------: | :------------------------------------------------------: | :------------: | :---------------------------------------------: |
|    FPADD    |  VLD(1)+JUMP(1)+LOOPS(10)+COND(7)+DLY(3)+INC(4)+CODE(4)  |     29bit      | 同一 FPADD 的 2 条指令（地址 0、1）长度完全一致 |
| UR（R0/R1） | VLD(1)+JUMP(1)+LOOPS(10)+COND(7)+DLY(3)+INC(4)+CODE(≥12) |     ≥38bit     |       同一 UR-R0 的 2 条指令长度完全一致        |
|    RtoVR    | VLD(1)+JUMP(1)+LOOPS(10)+COND(7)+DLY(3)+INC(4)+CODE(≥6)  |     ≥32bit     |       同一 RtoVR 的 2 条指令长度完全一致        |

可见：不同模块的微指令长度不同，但同一模块的指令长度固定，既满足解码需求，又兼顾功能灵活性。



### 疑惑点：指令可变长度，怎么解码？

**按道理说是长度固定，然后某几个字段代表代表当前是什么操作，然后通过这几个字段判断什么操作然后交由硬件进行处理**

## 一、先明确核心结论

AIACC 的设计逻辑和你理解的 “统一指令长度 + 运算字段标识” 本质一致，只是**把 “运算字段” 的功能提前到了 “指令队列分配” 阶段**：

- 通用 CPU：所有指令存在同一个队列，靠 “操作码（类似运算字段）” 判断执行什么操作、调用什么硬件；
- AIACC：不同 SMC 模块（如 FPADD、UR、RtoVR）有专属的指令队列（SMI-IQ），指令从一开始就存在对应队列里，硬件无需通过指令字段判断 “调用哪个 SMC”，只需解析本队列的指令即可。

而 CODE 字段长度不一致，完全不影响硬件判断 —— 因为**每个队列的硬件（IIC 指令发射控制器）都提前固化了本队列的指令格式**，相当于 “每个 SMC 都有专属的指令解码器”，只认自己队列的指令结构。

## 二、硬件如何判断 “做什么操作”？（分两步，无歧义）

### 第一步：通过 “指令队列 ID” 判断 “调用哪个 SMC”

文档明确说明：

- 每个 SMC 模块（FPADD、UR、RtoVR 等）对应专属的 SMI-IQ（指令队列），比如 FPADD 对应 “FPADD SMI-IQ”，UR 对应 “UR-R0 SMI-IQ”“UR-W0 SMI-IQ” 等；
- 每个 IQ 有唯一的`INST_ID`（指令队列编号），硬件通过`INST_ID`直接定位到对应的 SMC 模块，无需解析指令内容。

简单说：指令从哪个队列出来，就一定是给对应 SMC 的，比如从 “FPADD SMI-IQ” 出来的指令，必然调用 FPADD 模块，硬件不用判断 “该调谁”。

### 第二步：通过 “CODE 字段” 判断 “做什么具体操作”

每个 SMC 模块的功能是固定的，其对应的 CODE 字段格式也提前固化，硬件解析时直接按固定格式解读：

- 例 1：FPADD 模块的 CODE 字段（4bit），固定对应 “指令有效、源精度、目的精度、状态更新”（文档中 FPADD 微指令格式明确），硬件拿到 CODE 后，直接按这 4 个 bit 的定义解读，判断是 “32bit 浮点加法” 还是 “16bit 浮点加法”、是否更新状态寄存器；
- 例 2：UR 模块的 CODE 字段（≥12bit），固定对应 “Bank 编码、地址、读写使能”（文档中 UR 微指令格式明确），硬件拿到后直接解析 “读哪个 Bank、哪个地址”，无需关心其他模块的 CODE 格式。

核心逻辑：**CODE 字段的长度和含义是 “模块专属” 的，每个模块的硬件只解析自己的 CODE 格式**，就像 “每个部门有自己的工作手册”，不用管其他部门的规则，自然不会混乱。

## 三、为什么 CODE 字段长度可以不一致？（硬件层面的实现保障）

你担心的 “长度不一致导致硬件无法解析”，AIACC 通过 3 个设计完全规避了：

1. **每个 IQ 对应专属 IIC（指令发射控制器）**：IIC 是为特定 SMC 定制的，提前固化了该模块的指令字段定义（包括 CODE 长度、各 bit 含义），比如 FPADD 的 IIC 只认 4bit CODE，UR 的 IIC 只认≥12bit CODE，解析时直接按固定长度截取，不会出错；
2. **指令队列物理分离**：不同模块的指令存储在独立的 IQ 中，不会混合存储，硬件不会出现 “拿到一条指令不知道按哪种格式解析” 的情况；
3. **字段顺序固定**：同一模块的指令，字段顺序（VLD→JUMP→LOOPS→...→CODE）是固定的，IIC 按顺序解析，先读固定长度的公共字段（如 VLD、LOOPS 等），最后读本模块专属长度的 CODE 字段，解析逻辑简单且无歧义。

## 四、结合向量浮点加法样例，看硬件执行流程（直观理解）

样例中涉及 3 类 SMC 模块，对应 3 类 IQ，硬件执行时完全并行且无冲突：

|   指令队列   | 对应的 SMC | CODE 字段长度 |                         硬件判断逻辑                         |
| :----------: | :--------: | :-----------: | :----------------------------------------------------------: |
| FPADD SMI-IQ |   FPADD    |     4bit      | 1. 由`INST_ID`判断调用 FPADD；2. 解析 CODE={1,1,1,0}，按 FPADD 固定格式，判断为 “32bit 浮点加法、不更新状态寄存器”；3. 执行加法运算。 |
| UR-R0 SMI-IQ |  UR（读）  |    ≥12bit     | 1. 由`INST_ID`判断调用 UR；2. 解析 CODE={ur-rbank-0, ur-raddr-0, ur-re-0}，按 UR 固定格式，判断为 “读 Bank0 的连续 16 行地址”；3. 执行数据读取。 |
| RtoVR SMI-IQ |   RtoVR    |     ≥6bit     | 1. 由`INST_ID`判断调用 RtoVR；2. 解析 CODE={mv_out?_vld, mv_out?}，按 RtoVR 固定格式，判断为 “将 UR 数据转发到 FPADD 输入接口”；3. 执行数据转发。 |

整个过程中，硬件不需要 “统一解析所有指令”，只需要 “各管各的队列”，既避免了统一指令长度导致的位宽浪费，又保证了执行效率（专属硬件解析专属指令，无需复杂判断）。

简单说：AIACC 的设计是 “让合适的硬件干合适的活”，用 “模块专属队列 + 专属解析器” 替代了通用 CPU 的 “统一队列 + 统一解析器”，既解决了 “CODE 长度不一致” 的解析问题，又提升了 AI 计算的效率（这也是专用架构比通用架构在特定场景下更快的核心原因）。



### 那么指令一开始是怎么进入到对应模块的IQ里的

结合之前的样例，指令入队的完整流程的的定向性：

1. **宏指令解析**：MID 接收 “向量浮点加法” 宏指令，译码后确定需要调用的模块：UR（读数据）、RtoVR（数据转发）、FPADD（加法计算）、UR（写结果）。

2. **队列选择**：根据模块类型，MID 自动选中 4 个专属 IQ：UR-R0 IQ、UR-R1 IQ、RtoVR IQ（3 个）、FPADD IQ、UR-W0 IQ。

3. **指令写入**   将对应模块的微指令分别写入各自的 IQ：

	- UR-R0 的微指令（读 Bank0 数据）写入 UR-R0 IQ；
	- FPADD 的微指令（4bit CODE={1,1,1,0}）写入 FPADD IQ；
	- 其他模块的微指令也定向写入对应 IQ。

	

4. **指令发射**：每个 IQ 的专属 IIC（指令发射控制器）只解析本队列的微指令，发射到绑定的 SMC 模块。

整个过程中，指令的 “入队路径” 是固定的，不存在 “串队” 的可能。
