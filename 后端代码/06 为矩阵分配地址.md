```c++
int mm_assign_addr(MM_PARAM& param) {
  int cnt = 0;
  while (true) {
    int start_local_offset = (rand() % 5) * 64; 
    int L_start_npu = rand() % NPU_NUM; 
    int R_start_npu = rand() % NPU_NUM;
    if (!param.is_L_const) {
      param.L_addr = L_start_npu * LOCAL_MEM_SIZE + start_local_offset; 
```

 分配流程

- `start_local_offset`
- npu的localmemory来存放数据`L_start_npu`
- `L_start_npu * LOCAL_MEM_SIZE`

**（1）`if (!param.is_L_const)`**

- `param.is_L_const` **L 矩阵是不是常量（constant）**
- **不放到 per-NPU 的 ls**，而是放在 static 区因为：常放在 static/global 更合适，不需要反复，另一个主要用于保存中间激活、输入片段、输出片段等会经常读写的数据。

**（2）`param.L_addr = L_start_npu * LOCAL_MEM_SIZE + start_local_offset;` —— 这句的含义**

- `L_start_npu`：随机选了一个 NPU（例如 0、1、2…）
- `LOCAL_MEM_SIZE`
- `L_start_npu * LOCAL_MEM_SIZE`：就是**第 NPU 的 local 区在模拟器连续内存中的基地址**。
- `start_local_offset`
- 所以 `L_addr` = 第 `L_start_npu` 
	- 举例：`LOCAL_MEM_SIZE = 128KB`，`L_start_npu = 2`，`start_local_offset = 256`
		 → `L_addr = 2 * 128KB + 256`

**（3）不像真实 TPU 每个 NPU 真正独立**

- **真实硬件**：但对程序/虚拟地址来说，可以把每个 NPU 的 local 看成一个区块（NPU0 的区块、NPU1 的区块……）。
- **cmodel（仿真器）实现上**：通常一次性在内存中 `new` 或 `malloc` 出一大块连续内存（大小为 `LOCAL_MEM_SIZE * NPU_NUM`）。
	- 这样好管理。
	- `make_local_mem_from_continuous()` 就是把这块大内存按 NPU 切片并建立每个 NPU 的 `mem_arr[i]` 指针。

 为什么要 base（每个 NPU 的区域基准） + offset（在这一块里的偏移位置）

在仿真器里：

```
总内存 = LOCAL_MEM_SIZE * NPU_NUM
NPU0 local = [0, LOCAL_MEM_SIZE)
NPU1 local = [LOCAL_MEM_SIZE, 2*LOCAL_MEM_SIZE)
NPU2 local = [2*LOCAL_MEM_SIZE, 3*LOCAL_MEM_SIZE)
...
```

如果随机选中了 `L_start_npu = 2`

```
base = 2 * LOCAL_MEM_SIZE
```

- 前面可能已经为前一个 tensor 放了东西（比如随机放一个 A 矩阵）

因此你需要 

```
L_addr = base + start_local_offset
```

 offset 

如果所有 tensor 都从同一个 NPU 的 base 开始放：

```
L_addr = base
R_addr = base
Op2_addr = base
Y_addr = base
```

必须为每个 tensor 分配自己的空间：

```
L 从 base + 128 开始
R 从 base + 128 + L_size 开始
Op2 从后面继续
Y 从后面继续
```

这就是偏移的意义。

 为什么一开始需要一个偏移

`int start_local_offset = (rand() % 5) * 64; `

一开始 local memory 还没放任何 tensor，为什么不从 offset=0 开始放，而要随机给一个 offset？模拟真实 TPU 行为，并且用于测试寻址、对齐、跨 NPU 访存等逻辑是否健壮。**

完全不是因为内存已经有旧数据

-  **指定对齐**（如 16B、32B、64B）
- Local Mem 中可能已经存储其他算子的中间 tensor
- 多个 tensor 会放在 local mem 的不同位置

所以模拟器不能让你“从头开始整齐放”，这样会让代码只在特定情况能跑通，一旦换 offset 就全挂

 `(rand()%5) * 64`

 Local memory 的访问单位一般是 **64 Bytes 行（Row）**

- Sophgo BM1684X / 1688 / TPU 平常的 local memory 是 **按 64B 对齐访问**
- DMA、L2Load、Compute 等指令多数要求地址对齐到一定边界（16B, 32B, 64B）
- EU 取数据、tensor stride、bank interleave 都依赖 64B 对齐

所以偏移必须是 64 的倍数：

```
0, 64, 128, 192, 256
```

否则生成的地址不合法（不对齐）。

纯粹为了生成不同测试场景，但又不能偏移太大，否则很容易放不下。

例如 local mem 可能只有几十 KB，如果一上来就偏移太大，会出现：

```
start_offset 超出 LOCAL_MEM_SIZE
导致所有 case 都失败
```

所以：

- 5 个对齐块 → 0,1,2,3,4 行
- 不会太大，但能测试不同位置的寻址逻辑

这是一个非常聪明且简单的 fuzz 策略。



**TPU 的计算单元（EU/PE）是宽向量处理器，计算一个 Cycle 里要同时处理多个元素。**

例如（真实硬件等价的结构）：

- EU 一次处理 32 个 FP16
	 → 32 × 2 bytes = **64 bytes**
- 或一次处理 64 个 INT8
	 → 64 × 1 byte = **64 bytes**

所以：**每一次计算，EU 就要吃掉 64B 的数据包。所以 memory 也必须 64B 作为最小取数单位。**

**就是使用TPU计算必须每次给他64byte的数据，而且这个数据的起点是固定的，因为硬件就是这样设计的，不可能从中间开始取这样子**

假设 EU 要读一个 64B 的包，你给了它一个地址：

```
addr = 20
```

则硬件试图读取：

```
从地址 20 开始 → 要取 64B → 结束于地址 84
```

但是内存布局是这样：

```
0---63 | 64---127 | 128---191 | ...
```

- 既不属于第一条完整的 64B
- 又不是第二条的开始

硬件就无法一次性把这个“跨行的一整块数据”搬出来。
