# 静态调度、动态调度与异构流水

## 1. 调度责任的划分

调度问题应拆分为三个层次：

- **顺序**：哪些操作必须先于另一些操作；
- **发射**：某条就绪指令何时占用某个功能单元；
- **时间估计**：一次操作预计占用资源多久。

静态调度在编译期决定大部分发射次序和资源绑定；动态调度由硬件在运行时依据就绪状态和资源可用性选择发射。现实架构通常是混合体，不能简单归纳为“编译器知道周期”或“硬件只看依赖”。

## 2. 典型模型

| 模型 | 正确性由谁保障 | 性能主要由谁决定 | 代表机制 |
|---|---|---|---|
| 无互锁的静态发射 | 编译器必须满足延迟与槽位约束 | 编译器 | VLIW、软件流水 |
| 顺序发射 + 互锁 | 硬件阻塞未就绪操作 | 编译器排序 + 硬件停顿 | scoreboard/interlock |
| 乱序执行 | 硬件追踪就绪、重命名与提交 | 编译器和微架构共同作用 | reservation station、ROB |
| 多引擎命令队列 | 软件声明跨引擎依赖，队列内常按序 | 软件的 DAG 与硬件事件计数器 | DMA/compute queue、event |

即使在动态调度硬件上，编译器仍需处理内存别名、屏障、同步作用域和资源占用；即使在静态调度架构上，硬件也可能提供互锁或可变延迟单元。错误后果取决于 ISA 是否定义了停顿与冒险检测，不能一概而论。

## 3. BM1684X 的混合执行模型

根据当前源码可确认两类机制：

1. BD、GDMA 等引擎具有各自命令序列；
2. 命令包含 `CMD_ID` 与 `CMD_ID_DEP`，软件用编号表达跨引擎先后关系。

适合的抽象是资源受限 DAG：节点为命令，边为数据或同步依赖，节点还带引擎类型、预计周期、LMEM 区间和带宽需求。队列内顺序与跨队列事件共同决定可执行时间。

```text
GDMA(load tile i) ──event──> BD(compute tile i) ──event──> GDMA(store tile i)
          \                         
           └──── GDMA(load tile i+1) 可与 compute i 重叠
```

cmodel 中的周期公式可用于候选调度排序，但它是分析模型，不包含所有仲裁、带宽竞争和流水启动开销。正确方法是以真机测量校准，而不是把估算周期当作硬件承诺。

## 4. 从 layer group 到软件定义流水

传统 layer-group 优化按层或时间步安排 S2L、计算和 L2S。更前沿的做法是将粒度降低到 tile，并显式表示：

- 异步 copy 的发起与完成；
- 双缓冲或多缓冲状态；
- BD、GDMA、向量单元的资源占用；
- LMEM 生命周期和 bank 干扰；
- 动态 shape 下的合法调度范围。

PipeThreader 用 tile 级任务图搜索异构流水；Twill 将软件流水和 warp specialization 联合表述为约束问题；MPK 则进一步研究跨算子持久化执行。虽然目标硬件不同，但共同原则是：依赖边只保证正确性，资源与时延模型才决定流水质量。

## 5. 可落地的调度器设计

建议把后端调度划分为四个阶段：

1. **构图**：从 SSA、别名和布局信息生成精确依赖；
2. **资源建模**：为每个命令标记引擎、LMEM、带宽和预计周期；
3. **候选生成**：枚举 tile、buffer 数量、prefetch 距离和发射次序；
4. **验证与校准**：检查死锁、越界、依赖完整性，并用测量更新代价模型。

可优先实现确定性的启发式基线，再引入整数规划、约束求解或学习型代价模型。学习模型应预测解析模型的残差或候选排序，不应替代合法性检查。

## 6. 研究问题

- 能否从 `CMD_ID_DEP` 自动重建最小依赖图，并检测冗余屏障？
- 能否对 GDMA/BD/Vector 建立可组合的占用模型，预测流水气泡？
- 动态 shape 能否通过参数化调度或少量 guard 实现多版本流水？
- 能否用约束求解证明给定缓冲数下的最短稳态 initiation interval？
- 如何把端到端延迟、吞吐、LMEM 峰值与编译时间纳入同一多目标优化？
