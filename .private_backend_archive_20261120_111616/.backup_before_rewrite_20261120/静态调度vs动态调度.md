## 一、静态调度和动态调度，这两种编译器应该负责的部分不同，一种需要知道排具体的指令周期，另一种只需要依赖就可以

**第一种**：“让编译器来做指令排布，需要知道指令周期”

精确说法：编译器在**编译期**就决定每条指令占哪个发射槽、隔几个周期。它需要的不是笼统的“周期”，而是**每条指令的延迟（latency）、每个功能部件的占用情况、发射规则**。在纯静态架构里，排错不是“慢”，是**算错**。

**第二种**：“编译器不知道，硬件直接完成这个周期排布，编译器只需要知道依赖哪一条完成”

精确说法：硬件不是“排周期”，而是**在运行时根据实际完成状态决定何时发射**——发现操作数没准备好就等，准备好了就发。编译器（或固件）只**声明依赖**。排错的结果：不是慢，是**数据竞争（race condition），结果错**。

**两种模型里软件都有必须做对的事**，只是“必须精确掌握的东西”不同——一个是周期，一个是依赖。

## 二、静态调度：编译器排布（VLIW 一族）

### 机制

**VLIW（Very Long Instruction Word，超长指令字）**：一条“指令”其实是一个**指令包（bundle）**，里面并排放多条操作，每个槽位对应一个硬件功能部件。硬件每个周期把这个包整包取出、并行执行——**硬件完全不检查包内的依赖和冲突，照单全收**。

所以编译器必须：

1. 建数据依赖图（DAG）；
2. 知道每条指令的精确延迟（如“乘法 2 周期、访存 5 周期”）；
3. 用**表调度（list scheduling）**把无依赖的指令填进同一个包的不同槽位；
4. 没有合适指令可填的槽位，**显式填 NOP**（空操作）；
5. 跨循环体重叠迭代，即**软件流水（software pipelining）**。

### 代表硬件

| 硬件                                    | 说明                                                         |
| --------------------------------------- | ------------------------------------------------------------ |
| **TI C6000 系列 DSP**（C62x/C64x/C67x） | 教科书级 VLIW：8 个发射槽，编译器全权调度，排错直接出错误结果 |
| **Intel Itanium（IA-64，EPIC）**        | EPIC = Explicitly Parallel Instruction Computing，显式并行指令计算——名字直接宣告“并行性由编译器显式给出”。指令 3 条一束，束间用 stop 位标记依赖边界 |
| **早期 MIPS（R2000/R3000）**            | 见第六节的“名字彩蛋”                                         |
| **Qualcomm Hexagon DSP**                | 混合形态：4 条指令一个 packet（VLIW 血统），**但加了硬件互锁**，排错只会慢不会错 |

### 静态调度的代价

- **编译器极复杂**：调度器是编译器最难写的部分之一；
- **二进制绑死微架构**：延迟被编进了指令流，下一代芯片流水线变了，旧二进制就得重编。Itanium 的商业失败 partly 因此；
- **运行时不可变因素处理不了**：DDR 访存延迟随负载抖动，静态排布无法适应。

### 静态调度的收益

- 硬件极简：没有记分板、没有乱序逻辑 → 省面积、省功耗；
- 这正是 DSP/嵌入式场景要的：代码离线编译一次、精调到底，硬件便宜。

## 三、动态调度：硬件排布（乱序 CPU / GPU 一族）

### 机制演进（三代）

**第一代：记分板（Scoreboard），CDC 6600，1964 年（Seymour Cray 设计）**

> scoreboard = 记分板，一块记录“每个寄存器正在被哪条指令写”的状态表。
> 发射前查表：操作数没就绪 → 不发射（阻塞）；就绪 → 发射并登记。
> 这就是“依赖计数”的鼻祖。

**第二代：Tomasulo 算法，IBM System/360 Model 91，1967 年**

> 核心创新：**预约站（reservation station）**+ **寄存器重命名（register renaming）**+ 广播总线。
> 指令带着操作数（或指向生产者的标签）进预约站，谁的操作数先到谁先算，结果通过公共数据总线广播。
> 乱序执行（out-of-order execution）从此可行。

**第三代：ROB（Reorder Buffer，重排序缓冲），现代所有高性能 CPU**

> 乱序**执行** + 顺序**提交（commit）**：执行可以乱，但对外可见的结果按程序序写回。
> 配合分支预测、多发射，现代 x86/Apple M 系列每周期可执行 6~8 条微操作。

### 代表硬件

| 硬件                                 | 调度机制                                                     |
| ------------------------------------ | ------------------------------------------------------------ |
| **现代 x86**（Intel Core / AMD Zen） | 深度乱序 + ROB + 重命名                                      |
| **Apple M 系列、ARM Cortex-X**       | 超宽乱序                                                     |
| **ARM Cortex-A53/A55**（小核）       | **顺序双发射**（见第五节的中间形态）                         |
| **NVIDIA GPU**                       | warp 调度器：硬件记分板跟踪寄存器就绪状态，每周期从**就绪的 warp** 里挑；用**切换 warp** 来隐藏访存延迟（线程级并行掩盖延迟，而不是单线程内乱序） |

### GPU 的特殊性（和你的 TPU 最相关）

GPU 是“**动态调度 + 软件声明依赖**”的混合：

- warp 内指令级依赖：硬件记分板处理，编译器不用管周期；
- **跨线程/访存依赖：软件显式声明**——`__syncthreads()` / `bar.sync`（屏障指令）、CUDA 的 stream（流）和 event（事件）；
- `cudaStreamWaitEvent(stream, event)` 的语义 = “这个流里的后续操作，等 event 完成”——**和本芯片 `CMD_ID_DEP` 的语义一模一样**。

## 四、第三种形态：顺序执行 + 硬件互锁   也就是中间的一种形态

很多人漏掉这个中间形态，但它恰恰是“编译器要不要知道周期”的分水岭：

> **互锁（interlock）**：硬件检测到数据冒险（后一条指令的操作数还没写回）时，**自动插入停顿周期**。
> 编译器仍然决定指令**顺序**，但排得不优**只会慢，不会错**。

- 代表：ARM Cortex-A53/A55、几乎所有现代顺序核；
- 编译器还需要周期知识吗？——**正确性不需要，性能需要**（想跑快还是要排好顺序）。

## 五、硬件越完善编译器越简单，反之越复杂

```
编译器权力：大 ◄─────────────────────────────────► 小
硬件复杂度：小 ◄─────────────────────────────────► 大

  纯VLIW      顺序+互锁      粗粒度依赖计数      乱序执行
 (无互锁)                  （本TPU在这）        (OoO CPU)
 ─────────────────────────────────────────────────────►
 编译器需要   正确性不需要    只需要声明依赖      连性能都不太
 精确周期     只性能需要      (依赖+粗周期估算)   需要指令级周期
 (排错=算错)  (排错=变慢)     (依赖错=算错)
```

| 类别                           | 具体硬件                                     | 谁排时序                  | 软件需要周期吗               | 排错的后果           |
| ------------------------------ | -------------------------------------------- | ------------------------- | ---------------------------- | -------------------- |
| **纯 VLIW / 无互锁**           | TI C6000、早期 MIPS、Itanium(EPIC)           | 编译器                    | **必须精确（正确性）**       | **结果错**           |
| **顺序超标量 + 互锁**          | ARM A53/A55、早期 Atom                       | 编译器排序，硬件补停顿    | 只为性能                     | 慢                   |
| **粗粒度依赖计数**（你的 TPU） | **BM1684X**、NVIDIA NVDLA、GPU 的 DMA/stream | 硬件（依赖计数器）        | 不需要；粗估算用于优化       | **数据竞争，结果错** |
| **乱序 CPU**                   | x86、Apple M、Cortex-X                       | 硬件（记分板/ROB）        | 几乎不需要                   | （编译器很难排错）   |
| **GPU SM 内**                  | NVIDIA/AMD                                   | 硬件 warp 调度 + 软件屏障 | 部分（ptxas 做 SASS 级调度） | 屏障用错=错          |

## 六、bm在光谱上的精确位置（对照我们分析过的代码）

BM1684X 是**混合模型**，两个粒度机制不同：

### 引擎内部（如 BD 引擎）：静态顺序队列

```
命令逐条写入 BDC_CMD_BASE_ADDR 的连续槽位（WRITE_CMD_BD 的 write128）
→ 引擎按队列顺序执行（FIFO，先进先出）
```

软件不需要知道周期，因为**顺序语义**就足够了——不涉及重排。

### 引擎之间（BD ↔ GDMA）：动态依赖计数

```
命令字里的 CMD_ID / CMD_ID_DEP（bit 1–40）
→ 硬件各引擎维护完成计数器
→ poll_all_engine_done 里读引擎寄存器、比较计数：
   FW_READ32_WAIT_GE(BD_ENGINE_MAIN_CTRL, id_node->bd_cmd_id, 20, 2)
```

这就是**记分板思想的粗粒度版**：不是按寄存器记，而是按“命令编号”记。

### 为什么这个芯片选了这种设计？（四条理由，前两条是硬理由）

1. **存在运行时代码生成**。这套栈不全是离线编译——动态 shape 时 firmware **现场生成命令**（`api_route` → `sg_api_xxx` → `atomic_xxx_gen_cmd`）。运行时代码生成不可能维护一个周期精确模型，依赖计数让这件事变得简单：**只要依赖填对，怎么生成都对**。
2. **访存延迟不可预测**。卷积指令依赖 GDMA 把数据搬进 LMEM，而 DDR 延迟随负载抖动。静态排布会被内存抖动直接打穿；依赖计数天然免疫——“数据到了就开算”。
3. **软件栈简单**。编译器/固件只需要正确性知识（依赖、布局、对齐、值域），就是我们前一轮总结的那张表。
4. **指令流对固件升级更稳**。不像 VLIW 把周期数烧进二进制，依赖关系是语义信息，微架构调整不容易破坏它。

### 但注意：优化层仍然“像编译器一样思考时间”

`tpu-mlir` 的 TimeStep/LayerGroup 用**粗周期估算**做层级的软件流水——这其实是**静态调度思想在粗粒度的复活**：指令级交给硬件，

**层/时间步级由编译器排**。这是一个很漂亮的分工：

> **细粒度（指令）→ 硬件动态调度；粗粒度（层/时间步）→ 编译器静态规划。**

## 总结

> **静态调度把“时间知识”压给编译器（VLIW/DSP：排错=算错）；动态调度把“时间决策”收进硬件（乱序 CPU/GPU/本 TPU：软件只声明依赖）；本芯片是混合体——引擎内顺序队列 + 引擎间依赖计数器，并因为“运行时代码生成 + 访存延迟不可测”这两个硬约束，把指令级时间彻底交给了硬件，只在层/时间步的粗粒度上让编译器用周期估算做规划。**

如果你想继续深挖这条线，有两个自然方向：一是去读 `tpu-mlir` 的 `TimeStep`/`LayerGroup` 源码，看编译器怎么做粗粒度软件流水（那是“静态调度思想”在你这套栈里的真实存活处）；二是对照 NVDLA 的公开文档看它的依赖计数器寄存器设计，和 `CMD_ID` 机制互为印证。
