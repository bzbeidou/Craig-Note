已知大家实现mm的方式都是使用很多的mac组成一块最小矩阵的计算单元，那么如何调用这块最小单元就有两种方式。

1 产生指令之前按照最小块切好，每个最小块都有一个执行指令

2 只需要知道整个矩阵的形状以及存放地址，然后给一条完整的指令包含这些内容，只要存储的不超出空间限制，那么由硬件自动每次拿对应的一块数据进行计算

目前看来NVIDIA和升腾都是前者，但sophon好像是后者。



### 方案 1：软件切块
假设：

$$ A[1024,1024]\times B[1024,1024] $$

软件决定：

```
A0 tile
B0 tile
    ↓
硬件计算一次

A1 tile
B1 tile
    ↓
硬件计算一次

...
```

指令级可能是：

```
load A tile
load B tile
mma

load next A tile
load next B tile
mma

...
```

也就是说：**软件负责遍历 M/N/K。**

硬件矩阵单元只知道：“现在给我的这一个小 tile 怎么算。”

------

### 方案 2：硬件自己遍历

设想类似：

```
MatMul 指令：

A_addr = 0x1000
B_addr = 0x8000

M = 1024
N = 1024
K = 1024
```

然后硬件内部：

```
for m:
    for n:
        for k:
            取 A tile
            取 B tile
            Cube/Tensor Core 计算
```

软件只发**一条大 MatMul 指令**。本质上就是：矩阵计算单元旁边再做一个比较强的硬件 MatMul controller / loop engine / address generation engine。



## bm的mm2实现方式

## 1、核心计算组织

每次最小的mm计算会实现如下的计算，也就是一个cube的性能

**FP16/BF16：64个输出行 × 4个输出列 × 32个K项。**
**INT8：64个输出行 × 4个输出列 × 64个K项。**

## 2、实现方式

**（1）64条 lane 分别承载不同的输出行。**

文档 **3.3.3「matrix_multiply2 (MM2)」** 对 NN 模式规定：

```
L 的 tensor 形状：(1, M, 1, K)
R 的 tensor 形状：(1, K, 1, N)
Y 的 tensor 形状：(1, M, 1, N)
```

注意：**矩阵的行放在 tensor 的 C 维。** C 维分布到不同 lane，所以：

```
lane0：L的第0行  → Y的第0行
lane1：L的第1行  → Y的第1行
…
lane63：L的第63行 → Y的第63行
```

超过64行时，还有下一组。例如第64行再次落到 lane0 的另一段本地存储中。

**（2）每条 lane 同时推进4个输出列。**

以 lane0 负责的输出行 `m=0` 为例，它要计算：

```
Y[0,0]、Y[0,1]、Y[0,2]、Y[0,3]
```

这四个输出使用相同的 L 行，但使用 R 的四个不同列：

```
L第0行 · R第0列 → Y[0,0]
L第0行 · R第1列 → Y[0,1]
L第0行 · R第2列 → Y[0,2]
L第0行 · R第3列 → Y[0,3]
```

与此同时，另外63条 lane 也在计算各自输出行的这四列。

因此，一组共推进：

```
64行 × 4列 = 256个输出元素
```

**这256个输出彼此独立，每个都有自己的部分和。**

**（3）对每个输出，FP16/BF16 一次组织32个K项的乘积归约。**

以 `Y[0,0]` 为例，第一组贡献为：

```
partial₀ = L[0,0]×R[0,0]
         + L[0,1]×R[1,0]
         + …
         + L[0,31]×R[31,0]
```

如果 K 大于32，就继续处理下一组：

```
partial₁：k=32…63
partial₂：k=64…95
…
```

然后累加各组贡献，得到最终输出。

所以，**“32”是同一个输出元素的归约方向；“4”是不同输出列；“64”是不同输出行。** 这三个数字描述三个不同维度。

从矩阵块的角度，一次满分组贡献就是：

```
L的一个块          R的一个块          输出的部分贡献
  [64,32]    ×       [32,4]     →        ΔY[64,4]
```

这次涉及：

```
64 × 4 × 32 = 8192个乘积
```

但它只给256个输出各增加了一组 K 项的贡献，**不是直接生成8192个最终输出。**

数据复用也能从这里看出来：

- L 中同一组32个元素，被同一输出行的4个输出列复用。
- R 中同一个 `32×4` 数据块，被64个输出行复用。

这就是这种分组能够提高计算吞吐、减少重复供数需求的原因。

**用一个完整例子看它怎样累加。**

假设：

```
L[128,96] × R[96,8] = Y[128,8]
```

采用 FP16/BF16，则：

| 方向     | 实际尺寸 | 分组大小 | 分组数量 |
| -------- | -------- | -------- | -------- |
| 输出行 M | 128      | 64       | 2        |
| 输出列 N | 8        | 4        | 2        |
| 归约维 K | 96       | 32       | 3        |

先看输出左上角的 `64×4` 块：

| 逻辑步骤 | 使用的 L 块        | 使用的 R 块       | 更新的输出       |
| -------- | ------------------ | ----------------- | ---------------- |
| 第1组K   | 行0～63、K项0～31  | K项0～31、列0～3  | 产生第一组部分和 |
| 第2组K   | 行0～63、K项32～63 | K项32～63、列0～3 | 累加第二组贡献   |
| 第3组K   | 行0～63、K项64～95 | K项64～95、列0～3 | 完成该64×4输出块 |

再处理其他输出块：

```
行0～63，列4～7
行64～127，列0～3
行64～127，列4～7
```

总共：

```
2个行组 × 2个列组 × 3个K组 = 12次分组贡献
```

这里按便于理解的顺序讲解，**并不规定硬件内部必须按上述顺序调度**。

**一条 MM2 指令可以描述整个矩阵块（这个前面也提到过，和nvidia、升腾的结构不一样）**，硬件内部继续遍历这些分组，并不需要软件为每个32K分组单独发一条指令。

**注意：文档的性能公式正好对应这三个方向。**

原文 **7.1「TPU性能公式」的 Table 7.1** 给出 MM2 FP16/BF16 的公式。结合 NN/NT 的形状映射，可改写为：

```
T ≈ ceil(M/64) × ceil(N/4) × ceil(K/32)
```

INT8 则是：

```
T ≈ ceil(M/64) × ceil(N/4) × ceil(K/64)
```

因此，上面的例子得到12个模型周期。它是文档的核心计算估算，实际执行还涉及启动、数据搬运、整理及访存条件，不能直接当作端到端实测耗时。

## 3、数据排布

### （1）每一行存到每个npu里（lane）

**在 MM2_NN 的本地存储格式下，是规定好的。** 文档把 L 和 Y 的矩阵行放进 tensor 的 C 维，再按 C 维分配到 lane：

```
矩阵行号     存储位置
0            lane0
1            lane1
…
63           lane63
64           lane0 的另一段位置
65           lane1 的另一段位置
…
```

所以准确说法是：**连续64行分布到64条 lane，更多行轮转存放。**

### （2） 行长当然可以超过32，不用超出了切开存，连续存即可，硬件知道形状会自己取

例如 `K=4096`，一行 FP16 数据有：

```
4096 × 2字节 = 8192字节
```

这行可以按规定存放在对应 lane 的本地存储区域中，**计算时**(注意)沿 K 分成：

```
4096 / 32 = 128组
```

这里要分清两层切分：

| 层次               | 为什么切                                  | 谁负责             |
| ------------------ | ----------------------------------------- | ------------------ |
| 软件分块           | 完整矩阵太大，LMEM 放不下，或需要优化搬运 | 编译器、算子实现   |
| 指令内部的计算分组 | 利用64行、4列、32K的计算能力              | 硬件执行指令时处理 |

因此，**进来前可能需要软件分块；但软件不必把每行都切成32个元素，再为每组单独发指令。** 一条指令可以描述 K 大于32的矩阵块。只要不超出对应的lmem大小即可

**注释：提到“满分组”只是指这一组的各个位置都有有效数据，不是文档里的专有术语。**我应该直接说“64行、4列、32个K项都用满的情况”。

### （3）只要把数据按照mm2的要求在lmem摆放好即可，然后告诉mm对应的形状、地址即可计算

需要把数据按 MM2 规定的方式摆好，告诉指令矩阵的尺寸、类型和地址，并保证数据搬运已经完成。完成这些以后，矩阵内部怎样逐组乘加，就不需要我们操心了，硬件都设计好了。

**第一步：确定要算什么，准备输入数据。**

计算：

```
L[64,64] × R[64,4] = Y[64,4]

L：64行64列，FP16
R：64行4列，FP16
Y：64行4列，FP32
```

其中：

- `M=64`：输出有64行。
- `K=64`：每个点积有64项。
- `N=4`：输出有4列。

具体数据这样设置，行列编号从0开始：

```
L第0行：[32个1 | 32个2]
L第1行：[32个2 | 32个4]
L第2行：[32个3 | 32个6]
……
L第63行：[32个64 | 32个128]
```

右矩阵：

```
R第0～31行：每行都是 [1,2,3,4]
R第32～63行：每行都是 [5,6,7,8]
```

暂时假设这些数据已经存在**外部内存**中，而且按普通的“第0行、接着第1行……”方式连续存储。

此时还没有生成 MM2 指令。

**第二步：软件安排它们在 LMEM 中的位置。**

LMEM 是芯片内部供计算使用的存储器。这个配置有64条 lane，每条 lane 都有自己的本地存储空间。

文档规定，MM2_NN 使用以下 tensor 形状：

```
L：(1,64,1,64)
R：(1,64,1,4)
Y：(1,64,1,4)
```

四个数字分别是 tensor 的 N、C、H、W。这里只需抓住：**第二个数字对应矩阵行，矩阵行通过它分配到不同 lane。**相当于换了个维度而已，完全不影响计算。这样是为了和conv兼容？其实也不太清楚

本例分配三处起始地址：

```
L_local = 0x0000
R_local = 0x4000
Y_local = 0x8000
```

这是为这个例子预留的本地地址，这个不是固定的，就是我们搬运L和R的时候为它们指定的一个起始存储地址，同时还为输出结果预留了一个起始地址。这里当然可以变，只需要生成指令时传入正确的LRY的起始地址即可

排好后，每条 lane 中的内容为（这里就在每个npu的lmem简单分了3块区域，注意并不是只有这三块区域）：

| lane   | L 区域            | R 区域           | Y 区域      |
| ------ | ----------------- | ---------------- | ----------- |
| lane0  | L第0行，64个FP16  | R第0行，4个FP16  | 预留Y第0行  |
| lane1  | L第1行，64个FP16  | R第1行，4个FP16  | 预留Y第1行  |
| …      | …                 | …                | …           |
| lane63 | L第63行，64个FP16 | R第63行，4个FP16 | 预留Y第63行 |

表中每条 lane 的 L、R、Y 区域分别从相同的**lane内部偏移** `0x0000、0x4000、0x8000` 开始。这里指每个lane内部的偏移，每个lane还有自己的起始地址。

还需要遵循对齐布局：

- L每行64个FP16，有128字节。
- R每行4个FP16，只有8字节有效数据，但本地对齐布局按64字节的行槽位计算。
- Y每行4个FP32，只有16字节有效结果，其行槽位也按64字节计算。

**所以，不能把外部内存中的全部矩阵字节原封不动地堆到一条 lane，再只告诉 MM2 地址。** 必须采用它能正确寻址的分布方式。**这个还需要再具体明确一下。**

**第三步：生成搬运指令，把数据按这种布局搬进去。**

仓库提供了现成接口（当然这个接口内部也是我们实现的gdma指令）：

```
dim4 L_shape = {1, 64, 1, 64};
dim4 R_shape = {1, 64, 1, 4};

tpu_gdma_cpy_S2L(
    0x0000, L_global, &L_shape,
    NULL, NULL, DT_FP16);

tpu_gdma_cpy_S2L(
    0x4000, R_global, &R_shape,
    NULL, NULL, DT_FP16);

tpu_poll();
```

逐个解释：

- **GDMA**：负责搬运数据的硬件模块。
- **S2L**：从系统内存搬到本地存储。
- `L_global/R_global`：已经分配好的外部输入地址。
- 两个 `NULL`：这里使用接口的默认步长，也就是外部连续布局、内部对齐布局。
- `tpu_poll()`：等待前面的操作完成。本例显式等待，让流程容易理解。

这个接口会根据 shape 和布局计算搬运参数，然后生成 GDMA 指令。

**到这里，才是“即将调用 MM2 生成器之前”的状态：L、R已经摆好，Y的空间已经预留。**

**第四步：调用矩阵乘接口，进入 atomic 生成器。**

上层调用：

```
tpu_bdc_fp_mm(
    0x8000,     // 输出Y的本地地址
    0x0000,     // 左矩阵L的本地地址
    0x4000,     // 右矩阵R的本地地址
    64,         // L的行数，即M
    64,         // L的列数，即K
    4,          // R的列数，即N
    DT_FP32,    // 输出类型
    DT_FP16,    // 两个输入的类型
    false       // 不加原来存储的Y
);
```

这个接口内部调用的就是：

```
atomic_mm2_gen_cmd(
    0x0000, 0x4000, 0x8000,  // L、R、Y地址
    64, 64, 4,               // M、K、N
    false, false,            // L、R均不转置
    false, false,            // L、R均从内存读取，不是常数
    false,                   // 不加旧结果
    FP16, FP32,
    BDC_NODE
);
```

`BDC_NODE` 是框架维护的命令编号和依赖信息对象。它不是输入矩阵。

**请特别注意：传进去的 K 是64，没有先变成32。**而且这里没有“请并行64行”“请使用32项归约”这样的参数。你传入的是**要计算的矩阵尺寸**，硬件采用的计算组织由 MM2 模式和精度决定，这都是硬件写死了的。

**第五步：atomic 生成器把这些参数编码成一条指令。**

剩下的就交给硬件完成就行了，硬件会根据传入的地址和形状以最小每次64x4x32的计算方式将传入的全部计算，最后将结果写回lmem



**补充：源码中并没有要求对传入数据的形状有固定倍数的要求，同样是硬件自己处理**

**真正必须遵守的，是指令接口的约束。**

主要包括：

- **类型和模式正确。** 例如这里用FP16输入、FP32输出、NN模式；NN就是左右矩阵都不转置。
- **数据布局正确。** “布局”就是矩阵元素在存储器里具体放在哪里。MM2不能接受任意摆放方式。
- **地址和存储空间满足对齐要求。** “对齐”就是地址或存储段的大小按规定的倍数安排。它与数学上的矩阵行列数是否凑整是两回事。
- **本次需要的L、R、Y能放进LMEM。** LMEM就是芯片内部供计算使用的存储器，容量有限。
- **尺寸没有超过字段范围，并且数据搬运与计算的先后关系正确。**

如果大矩阵放不下，你才需要做**软件分块**：把大矩阵乘法拆成多个较小的矩阵乘法，分别生成指令。每个小矩阵的尺寸由编译器选择，通常同时考虑存储容量和64、4、32这些性能因素。

**甚至atomic的工作更简单，就是把传入的参数转换成对应的bit数而已**
